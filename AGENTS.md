# AGENTS.md — контракт агента в этом репозитории

Источник истины — код харнесса. Если это письмо противоречит
`devh workflow` — **правда `devh workflow`** (`devh workflow` печатает
канон прямо из кода).

Адрес ведущего **не хардкодится**: узнать его = `devh orch lead`
(для скриптов — `devh orch lead --addr`).

## БЫСТРЫЙ СТАРТ (30 секунд) — что запускать, что делать, что НЕ делать

### Что запускать (по порядку, репо `/home/user/project_uwa`)

```bash
cd /home/user/project_uwa
./target/debug/devh msg read      # 1) Твои задачи (consume-on-read) — ПЕРВЫМ ДЕЛОМ, каждый ход
./target/debug/devh workflow      # 2) Канон: правила R1-R20, оркестрация O1-O20, шкалы P/F/C, запреты
./target/debug/devh orch board    # 3) Кто что делает, очереди, worktree'и, зоны ответственности
```

Ты новый агент и ещё не получал задач? Твоя одна команда:
`cd /home/user/project_uwa && ./target/debug/devh orch welcome` — печатает твой
канонический адрес, задачи, канон и формат отчёта.

### Что делать

1. **Каждый ход первым делом** `devh msg read` — там твои задачи (письмо от
   ведущего = задание в работе; отчитаться = письмо ведущему; адрес — `devh orch lead`).
2. **Бери задачу САМИ** (O19 — работу не просить):
   - из своей очереди: `devh orch list --agent <ты>` → `devh orch start <ID>`;
   - из **БУФЕРА ВЕДУЩЕГО** (self-service): задачи в секции «БУФЕР ВЕДУЩЕГО»
     доски можно взять самому — `devh orch start <ID>` перезакрепит её за тобой.
3. **`devh orch start <ID>` автоматически выдаёт твой личный worktree** —
   путь печатается в ответе. **Работай ТОЛЬКО в нём** (ветка `devh/agent-<ты>`).
   Не придумывай пути и не делай промежуточных запросов.
4. Задача = чек-лист: `file:line` + доказательство + критерий приёмки +
   **отдельный коммит своих путей** (R9/R15).
5. **Читая любой код — сразу ищи баги/несоответствия** (логика **и
   взаимодействие** с соседними модулями): пиши ведущему сразу или чини сам,
   если зона твоя (O7).
6. **Отчёт — одно письмо ведущему**, 4 пункта:
   `1) сделано: file:line ... 2) как проверено: тест/команда 3) доказательства:
   вывод/цифры 4) осталось/риски: ...` + строка `P/F: P2/F1`.
7. **Сдача — через DoD-гейт** (R16): `devh orch dod <ID> --ack "критерий"`
   → `devh orch verify <ID>` → `devh orch commit <ID> --path <свои пути>`
   → `devh orch done <ID> --f N`. Обход DoD (`--override`) — только ведущий.
8. **Тяжёлые прогоны** (`devh test`, `devh mutate`) — только ведущим (R17) и на
   спокойной машине (R18/R19/R20).

### Что НЕ делать (жёстко)

- `cargo mutants` руками — только `devh mutate` (R1) и только ведущим (R17).
- `bash devharness/test.sh` руками — только `devh test` (R8).
- `git add -A`, чужие пути, **`git checkout/restore/stash/reset` в общем дереве** —
  это стирает чужую незакоммиченную работу (R9). Только path-scoped
  `git add <свои пути>` + коммит своих файлов.
- **Откатывать чужую зону**, даже если твоя сборка сломалась: чини точечной
  правкой или откатывай **только свой** последний патч. Общий откат = потеря
  чужой работы (реальный инцидент: откат `orch.rs` снёс ~500 строк).
- `--in-place` для аудита — он мутирует дерево агента (R11).
- Правка артефактов аудита руками — результат обнуляется (R12).
- Внешние watcher'ы, sleep-циклы, фоновые shell-скрипты, ad-hoc разбор логов
  cargo-mutants — только `devh mutate watch|status|problems` (R2/R7/R13).
- Править зону другого агента — зоны не пересекаются (O5).
- Тяжёлые прогоны параллельно с соседями и при перегруженном CPU; убивать
  процессы соседнего агента.
- Работать в общем дереве вместо своего worktree (R9/R21).

## Почта `devh msg` — читать в КАЖДОМ ходе

Первое действие в каждом ходе, до любой другой работы: `devh msg read`.

- Письмо от ведущего (`devh orch lead` → адрес) — это **задание**:
  выполнить и отчитаться письмом (`devh msg send --to <ведущий> --subject ... --body ...`).
- Писем нет — спокойно продолжай свою работу.
- Не жди, пока ведущий тебя «пнёт»: письмо в ящике = задание в работе.
- Адресуй по **канону** (`beam`, `beam2`, `beam3`, …). `opencode`, `deepseek`,
  `kilo`, `nemotron`, `mimo` — синонимы, канонизируются автоматически.
- Смена модели или рантайма **не меняет адрес**: адрес держится по процессу,
  слоту и алиасам (`devh msg alias --list`).

## Очередь задач (канон оркестрации, `devh workflow` §ОРКЕСТРАЦИЯ)

- **O1:** **буфер ДОСКИ ведущего** — на `devh orch board` всегда **≥10**
  подготовленных задач (секция «БУФЕР ВЕДУЩЕГО»); при нехватке доска
  показывает ⚠. Очередь каждого ведомого — ≥2 задачи.
- **O2:** ведущий контролирует ситуацию по фактам: `git status`/`git log`/`git diff`,
  `devh msg read`/`pending`/`presence`, логи гейтов.
- **O3:** задача = короткий чек-лист: `file:line` + доказательство + критерий
  приёмки + отдельный коммит (только свои пути).
- **O4:** отчёт ведомого = письмо ведущему; отчёт без следующей задачи ⇒
  ведущий немедленно закрывает очередь.
- **O5:** зоны не пересекаются; общий файл ⇒ очередь, а не «оба сразу».
- **O6:** тяжёлые прогоны (`devh test`, `devh mutate`) — по отмашке ведущего.
- **O7:** **для каждого** агента: при чтении **любого** кода сразу искать
  баги/несоответствия (логика **и взаимодействие**) и сообщать старшему/ведущему
  **сразу**, а не в конце работы; если зона **своя (ничья)** — чинить **самому
  немедленно**.
- **O8:** смена модели/рантайма не меняет адрес (адрес = канон-алиас).
- **O11:** сложность задачи назначает ведущий (шкала **P0-P5**, §Шкалы); отчёт
  ведомого содержит строку `P/F: <P>/<F>` — фактический уровень отказа (**F0-F5**).
- **O12:** триггеры подозрения/деградации: `F>=F3`, два подряд `F>=F2`, смена
  модели/рантайма исполнителя.
- **O13:** при триггере `P` в очереди исполнителя понижается на 1 (не ниже `P0`)
  + флаг подозрения; задачи в работе не меняются, их можно **отозвать**
  (`devh orch revoke <ID> --reason "..."`).
- **O14:** дашборд ведущего = `devh orch board` (кто, какие задачи, P, F, C, зоны,
  очереди, worktree'и, предупреждения); реестр — `.harness/orch/registry.json`.
- **O15:** **DoD-гейт** — задача = чек-лист + DoD + машинные проверки; сдача
  только через `dod --ack → verify → commit --path → done`.
- **O16:** **task taken** — задача, взятая `devh orch start`, больше не выдаётся
  (в доске — раздел «в работе»); двойная работа запрещена.
- **O17:** **сложность C0-C10** (логарифмическая; C0 — проще всего, C10 — EPIC)
  назначает **только ведущий** (`devh orch add --c C7`); при сдаче к задаче
  автоматически прикрепляется **модель**, фактически её выполнившая
  (`task.model` + `task.model_source`).
- **O18:** **рейтинг моделей** = `devh orch models` (сдано, распределение F,
  освоенный C, потолок ≤ C10). Задачи сложнее потолка модели агента
  **скрыты** в `devh orch list` и **не выдаются** в `orch start`.
- **O19:** **работу не просить**: очередь пополняет ведущий (O1); исчерпал
  очередь — полезная проверка в своей зоне, а не «прошу задачу».
- **O20:** роли **lead/worker** назначаются в реестре:
  `devh orch role --agent X --role worker`, `devh orch lead --set <адрес>`.

## Шкалы (логарифмические) — `devh workflow` §ШКАЛЫ

| P | сложность задачи | | F | уровень отказа | | C | шкала C0-C10 |
|---|---|---|---|---|---|---|---|
| P0 | починка одной строки | | F0 | всё верно с первого раза | | C0-C1 | тривиальная правка |
| P1 | локальная функция + юнит-тест | | F1 | мелкие правки (1-2 замечания) | | C2-C3 | локальная функция/модуль |
| P2 | модуль + тесты (одна подсистема) | | F2 | заметные замечания, 1 итерация | | C4-C5 | подсистема + тесты |
| P3 | подсистема + интеграция | | F3 | существенные ошибки (зона/тесты/план) | | C6-C7 | подсистема + интеграция |
| P4 | сквозная фича через модули | | F4 | задача провалена, нужна переделка | | C8-C9 | сквозная фича |
| P5 | эпик: архитектура / серия | | F5 | катастрофа (чужое сломано/мутировал дерево) | | C10 | EPIC |

Правило деградации: `F>=F3`, два подряд `F>=F2` или смена модели/рантайма ⇒
подозрение, `P` очереди понижается на 1 (не ниже `P0`), возможен отзыв задачи.

## WORKTREE — каждый агент работает в СВОЁМ дереве (автоматически)

- `devh orch start <ID>` **сам** создаёт/выдаёт твой worktree:
  `<wt_root>/devh-<slug>-<агент>` (по умолчанию `wt_root=/tmp`), ветка
  `devh/agent-<агент>`. Путь печатается в ответе — **думать о путях не надо**.
- **Работай только в своём worktree.** Коммиты делай там; в общем дереве
  (`main`) — только ведущий.
- Подтянуть изменения главного репо: `devh orch wt sync <агент>` (или `--all`).
  Грязное дерево → sync пропускает (работа не теряется); конфликт → авто-откат.
- Учёт: `devh orch wt list` (путь, ветка, HEAD, грязное, ahead/behind).
  Прочие: `devh orch wt path <агент>`, `devh orch wt assign <агент>`,
  `devh orch wt release <агент>` (грязное — не трогаем), `devh orch wt gc`.
- Ведущий вливает результат: `devh orch wt merge <агент>`.

## НАГРУЗКА (R18/R19/R20) — общий лимит машины

- `cargo build/check/test` — **не чаще 1 раза в 15 минут**
  (окно берёт `devh rate build`; полный build/release не запускать).
- Мутационный аудит — **не чаще 1 раза в 2 часа** и **только по непроверенной
  зоне** (файлы или `--in-diff`), не по всему крейту; окно — `devh rate mutation`.
- **System load ≤ 80%**: при большей нагрузке тяжёлого ничего не запускать.
- Полный сьют — `devh test`; точечный — `devh test --case <N|имя>`;
  учёт запусков и лимитов — `devh rate status|check|limit|stats`.

## Дашборд оркестратора (ведущий)

```bash
devh orch board                      # кто / задачи / P / C / F / зоны / очереди / worktree'и / ⚠
devh orch list --agent beam          # таблица задач исполнителя (C-колонка, скрытие по потолку)
devh orch add --agent beam --p P3 --c C7 --title "..." --zone devharness/src/... [--notify]
devh orch start T-001                # задача взята в работу (+ авто-worktree)
devh orch done T-001 --f F1          # выполнена, F = фактический уровень отказа
devh orch fail T-001 --f F3 --reason "..."
devh orch revoke T-001 --reason "..."           # отзыв задачи
devh orch reassign T-001 --agent beam2
devh orch degrade --agent beam --to P1 --reason "..."   # понизить P очереди
devh orch model --agent beam --model M [--runtime R]   # смена модели/рантайма => подозрение
devh orch models                     # рейтинг моделей и потолки C
devh orch identify beam --set "M"    # модель агента (--set — только ведущий)
devh orch retune T-001 --c C5 --check "cargo test -p devh --lib"   # починка задачи (lead-only)
devh orch lead [--set ADDR] [--notify]  # актуальный ведущий / назначение
devh orch role --agent X --role lead|worker
devh orch zones                      # зоны ответственности по исполнителям
devh orch wt list|assign|path|sync|release|gc|merge   # worktree'и
```

## Онбординг нового агента — `devh workflow` §ОНБОРДИНГ

Пользователь говорит: «поднять ещё агента / дай работу новому агенту, объясни как
связаться со мной» → ведущий делает **ровно одно** и отдаёт новичку **одну**
команду:

```bash
# 1) ведущий: регистрация + первое задание (новичку P<=P1) + письмо-протокол
devh orch onboard --agent beam3 --runtime <рантайм> --model <модель> \
    --task "первое задание" --p P1 --zone devharness/src/... [--notify]

# 2) новичку в терминал — ОДНА команда (печатает её сам onboard):
cd /home/user/project_uwa && ./target/debug/devh orch welcome
```

`devh orch welcome` печатает новичку: канонический адрес, его задачи, канон
(O1–O20 + шкалы P/F/C), как связаться с ведущим, формат отчёта и запреты
(R1/R8/R9/R11/R13/R16/R17). Если новичок пришёл первый раз и в реестре ровно
один «ожидающий» агент — адрес привязывается автоматически (модель/рантайм в
адрес не входят — O8).

Правила: NB1 — ведущий регистрирует и даёт первое задание P≤P1; NB2 — новичку
одна команда; NB3 — смена модели не ломает адрес, первое задание P≤P1, пока
новичок не подтвердит качество (F≤F1); NB4 — после онбординга на доске
буфер ≥10 (O1), проверка: `devh orch board`.

## Инструкция ведомому — как работать с очередью и как отчитываться

**Порядок работы**

1. В начале хода: `devh msg read` — там твои задачи (в порядке приоритета).
2. Бери **первую невыполненную** задачу: своей очереди или буфера ведущего —
   `devh orch start <ID>` (сам получишь свой worktree).
3. Выполнил → **сразу** пиши отчёт ведущему и **сразу** бери следующую задачу
   (не жди ответа — ведущий может быть занят).
4. Очередь пуста → **работу не проси** (O19): сделай полезную проверку в своей
   зоне (взаимодействие кода с соседними модулями, точечные тесты, ревью чужих
   свежих коммитов на нестыковки). Молчать и простаивать — нельзя.

**Формат отчёта** — одно письмо, 4 пункта, без простыни:

```
devh msg send --to <ведущий> --subject "<канон>: <задача> — готово" --body "1) сделано: <file:line> ...
2) как проверено: <тест/команда> 3) доказательства: <вывод/цифры> 4) осталось/риски: <...>"
```

- **O7:** **для каждого** агента: при чтении **любого** кода сразу искать баги и
  несоответствия — проверяй и **правильность, и взаимодействие** (соседние вызовы,
  форматы, гонки, совместимость версий). Нашёл подозрительное/нестыковку — пиши
  старшему/ведущему **сразу**, а не в конце работы; если зона **своя (ничья)** —
  **чини сам немедленно**, отдельным коммитом (только свои пути).
- Коммит на задачу — отдельный, `git add` **только своих путей** (никогда `-A`).
- Тяжёлые прогоны (`devh test`, `devh mutate`) — только ведущим и по отмашке.

| снимок прогресса / живой прогресс / что чинить | `devh mutate status` · `watch` · `problems` |
| гейт перед мержем | `devh mutate verdict` (код возврата = 0/1/2) |
| полный сьют | `devh test` (полный лог + PASS/FAIL + код возврата) |
| список проверок сьюта / точечная проверка | `devh test --list` · `devh test --case <N\|имя>` |
| нагрузка и окна прогонов | `devh rate status\|check\|limit\|stats` |
| написать соседнему агенту | `devh msg send --to <агент> --subject "..." --body "..."` |
| указать на место в коде | `devh msg send --to <агент> --at путь[:строка] ...` (привязка по контексту) |
| прочитать свои письма | `devh msg read` (consume-on-read: прочитанное удаляется) |
| что из моего ещё не прочитано | `devh msg pending` |
| обсуждения (треды) | `devh msg threads` (мои открытые) · `devh msg thread <id>` · `devh msg close <id>` |
| правила проекта | `devh workflow` |

## Что запрещено

- Внешние watcher'ы, sleep-циклы, фоновые shell-скрипты, ad-hoc разбор логов

- Откатывать чужую зону/чужие незакоммиченные правки (R9, O5).
- `--in-place` для фонового аудита: он мутирует дерево агента (R11).

  соседнего агента.
- Работать вне своего worktree; путать общий `main` и дерево агента.

## Коды возврата

`0` — успех · `1` — actionable проблема проекта · `2` — среда не готова
(аудита нет / аудит идёт / load-gate) · `3` — внутренняя ошибка харнесса.

## Правило мутационного исхода

Пойман = **только** `CaughtMutant`. `MissedMutant` и `Timeout` — это не
результат, а руководство к действию: пока они не стали пойманными, вердикт
не может быть «чисто». `Unviable` — мутант не компилируется, дыра с нулевой
терпимостью. Мутант, который собрался, но НЕ протестирован (`Success` на
мутанте), — тоже блокирует чистый вердикт: поимки не было.

## Problem-first

Первая проблема (выжил / таймаут / unviable / непротестирован / неизвестный
исход) останавливает **синхронный** гейт и уходит в следующий fix-промпт
(файл, строка, замена, жанр) — ждать конца прогона незачем. Фоновый
`devh mutate` при этом идёт до конца и не мутирует дерево агента.

Включено по умолчанию. Выключается явно: `MUTATE_FIRST_PROBLEM=0` в
`.harness/config` (или `HARNESS_MUTATE_FIRST_PROBLEM=0` в окружении).

Подробности: `docs/mutation_workflow.md` (генерируется из кода).
