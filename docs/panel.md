# ПУ — панель управления оркестратором (HTMX-сервер)

**Статус:** реализовано в рамках T-571 (P0). Ветка `devh/agent-ag-cd51d769`.
**Назначение:** единый read-only пульт над состоянием оркестратора devh: что работается,
что ждёт решения с наивысшим приоритетом, что сломано, что зависло в git и какова скорость агентов.

---

## 1. Принципы

1. **Read-only по построению.** Панель только читает: реестр (`.harness/orch/registry.json`),
   почту (`$DEVH_MSG_HOME`), git и `docs/`. Ни одной кнопки, меняющей состояние, в разметке нет
   намеренно. Мутации остаются в CLI (`devh orch …`), где есть гейты, реестр и журнал.
2. **Один канон — одна правда.** Скорость берётся из `core/throughput*`, очередь/буфер — из
   `core/board_view.rs` и `core/dashboard_projection.rs`, кандидаты веток — из `wtman::discover()`.
   Панель не строит собственный счётчик и не пересобирает реестр руками: расхождение панели
   с `devh orch board` — дефект, а не «особенность вида».
3. **Безопасно по умолчанию.** Bind только `127.0.0.1`; `0.0.0.0` запрещён. Никаких команд,
   которые меняют состояние, в рантайме панели нет. Тяжёлые операции (`git fsck`) — только
   по явному запросу пользователя.
4. **Без внешних зависимостей в рантайме.** HTMX вендорён в репозиторий
   (`core/panel/assets/htmx.min.js`), панель работает без интернета и без новых крейтов.
5. **Дёшево по времени ответа.** Тяжёлые сборки — под TTL-кэшем, авто-обновление страницы
   не тянет за собой полный пересчёт репозитория.

## 2. Архитектура

```
core/panel/                  данные (детерминированный снимок состояния)
  mod.rs                     PanelSnapshot + Summary + сборка
  tasks.rs                   активные/очередь/выполненные/инциденты/фичи
  agents.rs                  агенты: роль, модель, потолок, присутствие, скорость
  git.rs                     worktree'и, ветки, неслитый LOC, застой, WIP-ветки
  plan.rs                    docs/*.md: заголовок, mtime, markdown→HTML
  reports.rs                 отчёты lead/tech_lead из почты (признак «P/F:»)
  speed.rs                   скорость через core/throughput_collect (TTL 300 с)
  ledger.rs                  аудит прав: settings_ledger.jsonl
  assets/htmx.min.js         вендорённый HTMX 1.9.12
  assets/panel.css           тёмная тема

commands/dashboard.rs        HTTP-сервер (std::net): маршруты, рендер фрагментов
src/bin/devh-panel.rs        отдельная точка входа: devh-panel serve
```

Поток данных: `PanelSnapshot::collect(root)` → `fragment(section, snapshot, query)` → HTML-фрагмент.
Страница `/` рендерится целиком на сервере и содержит по одному `<section>` на раздел;
каждый раздел подтягивает себя через `hx-get="/panel/<раздел>"` с `hx-trigger="load, every 5s"`
и `hx-swap="innerHTML"`.

**Маршруты**

| Маршрут | Назначение |
|---|---|
| `GET /` | страница панели (каркас + все разделы) |
| `GET /panel/<раздел>` | HTML-фрагмент раздела (для `hx-get`) |
| `GET /panel/dangling` | недостижимые коммиты (`git fsck --unreachable`) — только по явному запросу |
| `GET /static/htmx.min.js` | вендорённый HTMX |
| `GET /healthz` | проверка живости сервера |

## 3. Разделы панели

### 3.1 Сводка (`/panel/summary`)
Плитки: в работе, в очереди, выполнено, P0 ждут, инциденты PS, агентов, работают,
LOC не слито, зависших веток, грязных worktree. Источник: реестр + git-сводка.

### 3.2 Агенты и модели (`/panel/agents`)
По каждому агенту: имя, роль (`lead`/`tech_lead`/`worker`), модель, рантайм, потолок C,
число активных задач и размер очереди, выполнено за 7 суток, LOC в ветке, минуты работы,
скорость LOC/ч, присутствие (presence) с возрастом, worktree, ветка, `merge_state`, признак
подозрения. Источники: `registry.agents`, `$DEVH_MSG_HOME/presence`, git-сводка.

### 3.3 Что работается сейчас (`/panel/active`)
Активные задачи (ID, P, C, зоны, агент, возраст, длительность), WIP-ветки и грязные
worktree'ы — то есть весь «застой» работы агентов, а не только формально активные задачи.

### 3.4 Очередь решений (`/panel/queue`)
Что ждёт решения с наивысшим приоритетом: queued P0/P1 первыми, по каждой задаче —
приоритет, C, агент, кто решает (`decision_owner`: lead/tech_lead), блокеры
(зависимости, превышение потолка, занятая зона). Источник: реестр + `plan.prio`/`plan.deps`.

### 3.5 Выполненные задачи (`/panel/done`)
Последние сданные задачи: ID, агент, `commit_sha`, `main_sha` (слит ли в main), фактический
уровень отказа F, длительность. Это же показывает расхождение «сдано, но не в main».

### 3.6 Git: worktree'и, ветки, LOC (`/panel/git`)
Worktree'и (владелец, ветка, грязна/чиста, ahead/behind), ветки `devh/*` с неслитым LOC
(от merge-base, `git diff --numstat main...branch`), зависшие ветки (без движения дольше
порога), WIP-ветки `devh/wip-*`. `git fsck --unreachable` — только по явному запросу
(`/panel/dangling`), numstat — под TTL-кэшем.

### 3.7 План (`/panel/plan`)
Файлы `docs/*.md`: заголовок, размер, время изменения; по клику — содержимое документа
в виде HTML (markdown → HTML с экранированием). Читается с диска: часть `*.md` находится
в `.gitignore`, из git план не берётся.

### 3.8 Отчёты lead и tech_lead (`/panel/reports`)
Лента канонических отчётов из почтового outbox: автор, роль, время, тема, тред, тело.
Признак канонического отчёта — строка «P/F:»; в карточке видны сводка «сделано» и P/F.

### 3.9 Инциденты и баги (`/panel/incidents`)
Открытые баги и инциденты (по классу: `bug_class` в реестре, приоритет, агент, зона),
психологическая безопасность (`PS`) выделяются отдельно. Сюда же — «аудит прав»:
последние записи `.harness/orch/settings_ledger.jsonl` (кто, когда, роль, источник прав,
цель, поле, было → стало, причина).

### 3.10 Рабочие фичи (`/panel/features`)
Группировка задач по тегам фич (`SEC-*`, `ПУ`, `RECLAIM-*`, `AUTOWIP-*`, `REVIEW-*` и т. п.):
что в работе, что в очереди, что сделано, кто исполнитель. Показывает именно РАБОЧИЕ
фичи, а не весь шум реестра.

### 3.11 Скорость агентов (`/panel/speed`)
За 7 суток: LOC взвешенный по сложности (`1.0 + 0.5·C`), WIP-LOC, thinking, токены,
коэффициент эффективности, доля thinking. Сбор — только через `core/throughput_collect`
(`core/throughput.rs`), TTL-кэш 300 с: сбор тяжёлый, авто-обновление страницы его не повторяет.

### 3.12 Аудит прав (`/panel/ledger`)
Отдельный фрагмент журнала `settings_ledger.jsonl` — кто и на каком основании менял
потолки/роли/модели. Append-only, только чтение.

## 4. Запуск

```bash
# отдельный бинарь (рекомендуется для дежурного режима)
cargo run -p devh --bin devh-panel -- serve --addr 127.0.0.1 --port 8787

# или через переменные окружения
HARNESS_PANEL_ADDR=127.0.0.1 HARNESS_PANEL_PORT=8787 devh-panel serve

# разовый снимок всех разделов в stdout (без сервера)
devh-panel once

# список маршрутов
devh-panel routes
```

Приоритет источников адреса: флаг `--addr/--port` → `HARNESS_PANEL_ADDR/HARNESS_PANEL_PORT`
→ `.harness/config` (`PANEL_ADDR`/`PANEL_PORT`) → значения по умолчанию (`127.0.0.1:8787`).
Bind вне loopback не допускается.

## 5. Обновление

Обновление — HTMX-таймер `every 5s` для всех разделов; ответы отдаются с
`Cache-Control: no-store`, поэтому состояние всегда актуально. SSE не используется:
в реализации на `std::net` это ручной keep-alive/фрейминг без выигрыша по сравнению
с таймером. Тяжёлые разделы дополнительно защищены TTL-кэшем (скорость — 300 с,
git-сводка — 30 с), поэтому цикл обновления не нагружает репозиторий.

## 6. Ограничения и дальнейшие работы

* Сейчас панель — наблюдатель; операции (merge, сдача, отзыв) выполняются только через CLI.
* Дальше по плану: `T-608` (решение по серверному стеку + `PANEL_ADDR/PANEL_PORT` в конфиге),
  `T-609` (каноническая очередь/буфер через `board_view`/`dashboard_projection`),
  `T-610` (разбивка скорости по периодам и моделям), `T-611` (guard read-only),
  `T-612` (inotify-сигнал о новой P0/PS), `T-613` (правка спеки по ревью).
  У tech_lead: `A` (запуск всех агентов только через devh — «ditch zed»),
  `D` (раздел «Git» через `wtman::discover()`), ревью спеки.
* `git fsck --unreachable` в этом репозитории даёт ~1688 недостижимых коммитов —
  поэтому он никогда не выполняется в фоновом цикле обновления, только по запросу.
