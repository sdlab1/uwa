## 1. Что случилось (инцидент ЧП)

Новый агент (сессия `session:20261024_1`) получил личность **lead** (`minimax`) и, как следствие,
доступ к lead-задачам и lead-правам. Причина — не «злой умысел», а **дефект идентификации**:

1. Агентские процессы запущены редактором (zed) напрямую: `bash` агента — **прямой потомок
   `zed-editor`**, а не процесса рантайма (`goose`/`opencode`/`kilo`). Поэтому runtime-детект
   (`runtime_ancestor()`) не находит рантайм → `devh msg whoami` печатает `рантайм ?`.
2. Идентификация падала в ветку **slot-привязки**: `slot:<pid редактора>:<starttime>:none`.
   Slot-привязка была `claimed=true` с именем `quarantine-slot-2669` → **любая** новая сессия
   в этом слоте наследовала чужое имя, а вместе с ним — права и очередь.
3. `resolve()` отдаёт сохранённую привязку по ключу сессии **раньше** проверки прав:
   имя/роль в реестре не сверялись с тем, кто за этим именем стоит.

**Оперативный фикс (сделано):** привязки в карантин
`/tmp/devh-msg/quarantine-identity-collision-20261024/`, slot-привязка обезврежена
(`claimed=false`, уникальное авто-имя `ag-0f7c4267`), сессия закреплена за отдельным
каноном, lead-команды закрыты паролем (`devh orch lead --set` → rc=1).

**Постоянные фиксы — в реестре:** T-213/T-214 (slot-идентичность), T-216 (EPIPE),
T-219 (потолки), T-227 (AUTHZ), T-232/T-233/T-236 (идентификация v2 + сторож).

## 3. Решение lead'а: единый workflow вместо бюрократии

Было: lead раздаёт задачи письмами → ведомый «берёт» из буфера lead → буфер = очередь lead →
письма-разгонщики. Стало:

* **lead не раздаёт задачи вручную** и **ведомые не берут** их из буфера;
* выдача — **одной командой агента** (`devh next`), которая сама выбирает следующую готовую
  задачу и сама её стартует (claim + worktree);
* «буфер ведущего» перестаёт быть источником ручной раздачи — это **общий пул**;
* DoD-гейт, guardrails, зоны и отчётность сохраняются.

Задачи: **T-232** (обязательная декларация модели), **T-233** (журнал идентичностей + сверка
с реестром), **T-234** (`core::dispatch` — выбор следующей задачи), **T-235** (интеграция в
`devh next`, удаление self-service из буфера lead), **T-236** (сторож: один канон = один ключ).

### Идентификация v2 — минимальный контракт

1. Агент **обязан задекларировать** модель и рантайм (`devh msg identify` / `devh orch identify --self`).
2. Без декларации: агент — worker, потолок **C0**, задачи не выдаются; lead-права невозможны.
3. Неизвестная модель → потолок **C1** (fail-closed), а не C5.
4. Роль `lead` — только явной записью в реестре; идентичность/слот/алиас прав не дают.
5. Один канон = один ключ сессии; второй ключ на то же имя → **отказ**, а не тихое слияние.
6. Расхождение «реестр vs декларация» → пометка и fail-closed (C0), а не тихий downgrade.
7. Журнал: `.harness/orch/identities.jsonl` (declare/claim/model_change/role_change/task_start/done).

## 4. Правила для lead'а (после ревизии)

* Не слать письма-разгонщики; отчёт — одно письмо lead'у **по факту сделки**.
* Задача = чек-лист: `file:line` + доказательство + критерий приёмки + DoD + `--check`.
* Задачи создаются сразу с DoD/check; распределение — автоматическое (после T-235),
  до этого — создание с явным `--agent`, без писем.
* Тяжёлые прогоны (`devh test`, `devh mutate`) — только lead и на спокойной машине.
* Перед коммитом: `git status` во всех worktree'ях; мёртвые worktree'и — `devh orch wt gc`
  (только после проверки, что там нет чужой работы).
