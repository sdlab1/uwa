## 0. Суть: три петли, и почему эта — самая дешёвая

В машине devh уже есть две петли обратной связи:

| Петля | Что ловит | Механизм | Статус |
|---|---|---|---|
| 1. код ← грабли | где падал код | `RULES_LOG`: merge дописывает «## Session N — <title> (<date>)» в todo/report.md; `cfg.rules` в промпте говорит «прочитай целиком» | есть |
| 2. спеки ← сессии | где спека была кривой | `plan.md` заметки между попытками; `RED-EXPECT` таксономия env/spec/honest (P7-1.1) | есть |
| 3. промпт ← слепота тестов | **где тесты слепы** | мутационные выжившие → очередь наблюдений → дистилляция классов → RULES + точки наблюдения в спеках | **этот план** |

Почему выжившие мапятся в промпт **прямее граблей**: у выжившего есть точные координаты и описание поломки, которую никто не заметил (файл: строка: колонка, жанр, текст замены). Грабель выражается текстом summary сессии, выживший дан уже почти в формате очереди наблюдений. Промпт получает структуру, а не пересказ. Нюанс: промпт-правила — про плотность ассертов **до** написания; мутационный вердикт — про качество **после**. Они не взаимозаменяемы, они слои.

И отдельное утверждение про RED, на котором держится P8-5: **RED-тест — первый тест фичи и почти наверняка единственный в этой зоне**. Плотность его ассертов сегодня = kill-rate будущих сессий в этой зоне. Поэтому «улучшать промпт, из которого рождается RED» — это не про честность гейта (она уже есть, P7-1.1), это про наследование качества ассертов от сессии к сессии: след от прошлой сессии в текущий промпт.

Почему дёшево: гейт **уже производит** данные в практически совпадающем формате. Не хватает трёх коротких модулей (`survivors.rs`, `killmap`, парсер `OBSERVE:`) — ни один не трогает вердикты гейта, kill-rate и дисциплину тикетов. Обратная связь — самый дешёвый из трёх контуров, потому что данные уже льются.

## 2. Архитектура петли

```
                      ┌──────────────────────────────────────────────┐
                      │  mutate_gate (commands/run.rs, finish×3)     │
                      │  прогон → mutants.out/outcomes.json (LIVE)   │
                      └───────────────┬──────────────────────────────┘
                                      │ MissedMutant'ы (+ метка гейта)
                  ┌───────────────────┴─────────────────────────────┐
                  ▼                                                 ▼
      (авто) .harness/observations.md                   (авто) .harness/killmap.json
      строка формата §3                                 файл → caught/missed/runs/last
      дедуп через survivors-seen.json                            │
                  │                                                 │
                  ▼                                                 ├──▶ (авто) agent_prompt: hot-spot top-3
      `devh tickets --import`                                     │     (prompt.rs, bounded ≈2 строки)
      тикет → fix-раунд                                           ▼
      ИНСТАНС → фикс                              (авто) devh hint: таблица kill-rate
                                                                  │
                                                                  ▼
                        (ЧЕЛОВЕК, дистилляция раз в N сессий — не автоматизация)
                        кластеры выживших → КЛАСС слепоты → RULES (слой §4)
                        класс молчит K сессий → ПЕНСИЯ (архив, не удаление)
                                                                  │
                   ┌─────────────────────────────────────────────┘
                   ▼
      agent_prompt (prompt.rs): cfg.rules + hot-spot + OBSERVE
                   │
                   ▼
      агент пишет тесты с прицелом на hot-spot зоны и по классам спеки,
      а не равномерно по файлу
                   │
                   ▼
      меньше выживших → kill-rate ↑ → killmap остывает → новые классы (петля жива)
```

Два правила тока данных, на которых держится честность (детали — §8):

1. **ИНСТАНС (конкретный выживший) в очередь/тикеты. НИКОГДА — в промпт.** Список «вот 40 мест, где мы ловили выживших» — балласт, он разжижает контекст и гниёт.
2. **КЛАСС (паттерн слепоты) в RULES/промпт. НИКОГДА — с координатами инстансов.** «В load.rs забыли ассерты» сгниёт; «обёртки получают контракт-тест» компаундится.

## 3. P8-1: выжившие → observations.md (автотриаж в существующую очередь)

**Цель:** каждый прогон гейта с выжившими сам дописывает их в очередь наблюдений — без ручного `grep` и без единого нового формата.

### Формат строки (обратная совместимость с tickets.rs — по построению)

```
devharness/src/core/load.rs:15 | survivor: replace load_average -> Some(0.0) [FnValue] | red-тест: ассерт точного значения load_average на фикстуре /proc/loadavg (и мусор → None), не is_some()
```

- поле 0: `<файл>:<строка>` — из `scenario.Mutant.span.start`;
- поле 1: `survivor: <хвост name после 'файл:строка:колонка: '> [<genre>]` — короткая природа поломки (`ticket_title()` даст «obs: devharness/src/core/load.rs:15 — survivor: …»);
- поле 2: `red-тест:` — **авто-идея по жанру** из таблицы §4 (дефолт при неизвестном жанре: «прямой ассерт результата на этой строке»). `tickets --import` примет строку ТОЛЬКО с этим полем — симметрия дисциплины «наблюдение без red-идеи не считается» сохраняется механически.
- метка источника: `[red-mutation]` в поле 1, если выживший пришёл из RED-гейта (второй мутационный конфиг); выжившие обычного гейта (`mutation`) без метки. RED-выжившие — другая зона ответственности (качество спеки, не кода), дистилляция их не смешивает.

### Что считается выжившим

`summary == "MissedMutant"` и только. `TimeoutMutant` в статистике devh считается убитым (kill-rate = (caught + timeout) / (total − unviable)), `UnviableMutant` — не про тесты, а RED-гейт — отдельная зона ответственности (помечена в очереди, см. выше).

### Дедуп

`.harness/survivors-seen.json` — набор SHA256(`file:line:col:mutation`): один и тот же выживший в очереди одно строкой, покуда не починен/не удалён вручную. Повторы **не дублируются в очередь**, но **считаются в killmap и журнал** (§5, survivors.log) — «вечный» выживший виден как растущий счётчик, что и нужно для пенсии/частости. Автоматический prune не делаем: per-file прогоны перезатирают outcomes.json, и «не видел хэш в этом прогоне» ≠ «выживший исправлен»; размер — единицы хэшей, не оправдывает риск.

### Точка врезки (точная)

`mutate_gate` (`commands/run.rs:1213`) — после **каждого** `run_mut`, а не после гейта: в batch-режиме один прогон на все файлы, в per-file — N прогонов, и каждый `cargo-mutants` перезаписывает `outcomes.json`. Значит хук ставим сразу после `finish()` в трёх местах (single / batch / per-file loop — run.rs:1320/1345/1383 по текущему дереву), а `early`-останов (P7-2.3) — тоже: убитый прогон оставляет валидный частичный `outcomes.json`, выжившие в нём настоящие.

Хук делает (`core/survivors.rs::collect_after_run` →):
1. `outcomes.json` из `wt.join(early::mutants_out_dir(&tool0))` (флаг `--output` уже парсит `early.rs`);
2. список `MissedMutant` → строки формата выше → `store.append_raw("observations.md", …)` **под `GlobalLock`** (как делает `tickets.rs::import`);
3. seen-дедуп: новые хэши → в `survivors-seen.json` + строка в `survivors.log` (`дата | гейт | файл:строка | genre | мутация`);
4. апдейт `killmap.json` (§5) — по всем исходам прогона, включая CaughtMutant;
5. одна лог-строка в вывод гейта: `survivors: 2 → observations.md (fn-value 1, binop 1)` — человек на окне терминала сразу видит поток.

`store.dir` нужен хуку: `mutate_gate` вызывается из `commands/run.rs:415` (red-mutation) и `:789` (mutation) — обе точки располагают `store`, прокидываем параметром (`obs: &Path`). Второй вариант — собирать по возвращённому `MutReport` на стороне call-site, но тогда per-file-режим теряет все планы кроме последнего: хук именно внутри.

### Конфиг

`MUTATE_SURVIVORS` — bool. Дефолт в коде `false` (по той же дисциплине, что `MUTATE_COV`: молчаливое поведение существующих установок меняем только явным ключом), а в шаблоне `commands/init.rs` пишется строка `MUTATE_SURVIVORS=1` с комментарием — новые окружения получают петлю сразу. Отключение = `0`. Больше никаких конфиг-ключей петле не нужно.

### Мелочь, обязательная к P8-1

`tickets.rs::import` — различать текст спеки тикета по префиксу `survivor:` в поле 1: «Тикет из мутационного триажа: тесты слепы в этой точке — red-идея обязательна, уточни ассерт по месту» (сейчас единый текст «из OnFlyAnalysis…»). Две строки в import'е, формат очереди не меняется.

### Приёмка P8-1

- юнит: фикстура `outcomes.json` (2 missed + 2 caught + 1 unviable + 1 timeout) → ровно 2 строки очереди, каждая с `red-тест:`; seen-дедуп: второй collect → 0 новых строк, killmap счётчик +2;
- интеграция: гейт с принудительно ослабленным тестом (A/B: локально точный ассерт на `max_load` из load.rs → `is_some()`, вернуть после прогона) → выживший появился в `observations.md`, `devh tickets --import` взял его в работу, формат очереди не сломан;
- неизвестный `summary`/отсутствующее поле → прощающий парсер (serde_json::Value, доступ по имени), один `WARN`, не паника.

## 4. Таксономия: жанр cargo-mutants → класс слепоты → правило

Класс называет **человек** при дистилляции; **жанр — только подсказка** для авто-идеи red-теста и для кластеризации. Ниже — базовый набор из шести классов, инициирующий слой RULES (первый — из нашего реального фикса P5/§9.12, а не из головы: `core/load.rs`, 2 MISSED в приёмке).

| Жанр (outcomes.json `scenario.Mutant.genre`) | Класс слепоты | Авто-идея red-теста | Правило-класс в RULES (тег) |
|---|---|---|---|
| `FnValue` (`replace -> None/Some(x)/значение`) | точность ассерта | ассерт точного значения (None/Some(x)/число/строка), не `is_some()`/`is_ok()`; граничные значения отдельно | `blind:fn-value` |
| `BinaryOperator` (`&&↔||`, `+↔−`, `&↔|`), `ComparisonOperator` | плечи условий и границ | кейсы на **оба плеча** каждого нового `if`/сравнения + граница (включая равенство) | `blind:boundary` |
| `MatchArmGuard`, `MatchArm` | непокрытые ветки | кейс на каждую ветку match; guard — отдельно | `blind:match-arms` |
| — (не жанр, метит человек) — обёртка/делегат | контракт обёртки | прямой контракт-тест **на результат** обёртки, не на факт делегирования; пример-происхождение: `core/load.rs` (`load_average`/`max_load`, 2 MISSED в приёмке, закрыты юнит-тестами `ae9f719`) | `blind:wrapper` |
| — env/config-чтение (`HARNESS_*`, parse from env) | env-чтение | тест с установленным значением, **со сброшенным** и на границе (мусор → дефолт) | `blind:env-var` |
| — чистая функция с операторами | операторная масса | один `proptest` с инвариантом вместо пяти эрзац-юнитов | `blind:pure-fn` |
| неизвестный/новый жанр (правило пересмотра) | — | дефолт: «прямой ассерт результата на этой строке, без толерантности» | пополняется таблицы при дистилляции |

Замечания по точности (чтобы план не врал):
- в наших прогонах встречались `FnValue`/`MatchArmGuard`/`BinaryOperator`, но это узкие файлы. Полный перечень жанров сверить по большому `outcomes.json` (255-прогон) в день имплементации — таблица пополняется, парсер не падает на unseen genre.
- Жанр ≠ класс один-к-одному: `FnValue` может оказаться и `wrapper`, и `pure-fn`. Авто-идея привязана к жанру, класс — решение человека; в `survivors.log` пишем genre (машинно), в RULES — тег класса (человеком).

### Формат слоя RULES (как он ляжет в todo/report.md)

```markdown
## Классы слепоты тестов (из мутационных выживших, P8)
- `blind:fn-value` Новая pub-fn с логикой получает прямой тест с точным ассертом
  (значение/None/Some(x)/граница), не is_some/is_ok. Признак в триаже: жанр FnValue.
- `blind:boundary` Новое if/сравнение/булево покрывается кейсами на оба плеча
  и на границу (равенство). Признак: BinaryOperator/ComparisonOperator.
- `blind:wrapper` Делегирующая pub-fn с добавленной логикой — контракт-тест на
  результат, не на делегирование. Признак: FnValue в тонких модулях (load.rs был первым).
- `blind:env-var` Чтение env/config — три кейса: установлено, сброшено, мусор на границе.
- `blind:match-arms` Каждая ветка match и каждый guard — отдельный кейс.
- `blind:pure-fn` Чистая функция с операторами — proptest с инвариантом, не пять юнитов.
```

Правило приёма в слой: **без координат инстансов** (`file:line` в RULES запрещены — это перевод класса в инцидент), формулировка «что делать», не «что было».

## 5. P8-3: hot-spot map (rolling kill-rate по модулям) → hint и промпт

**Цель:** агент пишет тесты с прицелом на исторически слабые зоны, а не равномерно.

### Данные

`.harness/killmap.json` (рядом с `.harness/coverage` — прецедент локального состояния):

```json
{
  "version": 1,
  "files": {
    "devharness/src/core/load.rs": {"caught": 33, "missed": 0, "runs": 2, "last": "2026-10-18"}
  }
}
```

Обновляется тем же хуком P8-1 (каждый прогон = приращение по `scenario.Mutant.file`; `missed/runs/last` заодно). Накопительно, без decay — пенсионные решения принимает человек (§6). Отсутствие файла среди мутантов прогона ≠ «0 killed»: если файл не мутировался (scope не задел), его строка карты не меняется.

### Куда смотрит агент и человек

- **`agent_prompt`** (`prompt.rs`, после строки про kill-rate): пул слабых зон — только файлы с `missed > 0`, топ-3 по `missed`, одна строка на файл:
  `Исторически слабые зоны тестов: <файл> (2 выживших / 3 прогона) — пиши ассерты тут плотнее: точные значения, оба плеча условий.`
  Жёсткий бюджет: ≤ 3 файла, ≤ ~200 символов пула; пусто → строка не добавляется. Kill-rate пула НЕ влияет на вердикт гейта (и это должно быть сказано в спеках — см. §8).
- **`devh hint`** (`misc.rs`, для человека): таблица файлов killmap с kill-rate (killed/total) и возрастом последнего прогона — «прицел» перед взятием следующей спеки.

### Приёмка P8-3

- юнит: фикстура `outcomes.json` → killmap.json обновлён корректно (caught+missed+runs инкремент, last-дата);
- юнит на пул: 5 файлов с missed → в промпт попадают ровно 3, строка ≤ бюджета; файлов без missed → блока нет;
- интеграция: после двух прогонов с разными `outcomes.json` (оба с missed в одном файле) killmap сходится к сумме.

## 6. P8-4: дистилляция — классы в RULES и пенсия (ручная петля + тулинг-поддержка)

**Цель:** раз в N сессий (напр. еженедельно, ~1 ч) человек превращает кластеры выживших в правила-классы и прогоняет нестреляющие правила на пенсию. Классификация слепоты — решение человека, не агента; автоматизируем только сборку фактуры.

### `devh survivors` (новая субкоманда, режимы)

- `devh survivors` — группировка `survivors.log` по `жанр × файл` со счётчиком повторов, самой свежей датой и примерами-хвостами мутаций (до 3). Выход: «вот за неделю повторялось: fn-value 4 (load.rs ×3, max_load.rs ×1), boundary 2 …» — материал для решения «класс? пенсия?».
- `devh survivors --rules --sessions 10` — по класс-тегам из RULES (`blind:*`): для каждого класса — последний выстрел (дата строки `survivors.log` с маппингом жанр→класс через признаки тега) и число сессий тишины; при тишине ≥ K — строка «на пенсию: обоснование — K сессий без выстрелов класса». Жанр→класс-маппинг человек подтверждает глазами (тег перечисляет свои жанры в тексте).
- `devh survivors --reset` — очистка seen (при фанатичной уборке очереди), редкий ручной инструмент.

### Пенсия

Класс молчит K сессий (дефолт K=10) → переносится из активного слоя RULES в раздел «Пенсион» **того же файла** (история не удаляется). Бюджет активного слоя: ≤ 12 классов (сверх — сначала пенсия). Если пенсионный класс внезапно выстрелил — возврат активным + строка урок в RULES («класс X, пенсионирован по тишине, выстрелил снова: …» — это уже грабель четвёртого рода, но бесплатно ловится killmap'ом).

### Строка сессии в RULES_LOG (merge.rs)

При merge рядом с «## Session N» дописывать: `- survivors: <классы, стрелявшие в этой сессии (из дельты killmap + survivors.log этой сессии)>` — дистилляция получает журнал по сессиям бесплатно, без ручного `tail`.

### Приёмка P8-4

- юнит: `survivors.log` с датами → `--rules` печатает «тишина K сессий» и метит пенсионеров; пустой журнал → «нет данных», не паника;
- интеграция: merge после сессии с missed дописал строку survivors в RULES_LOG (если ключ включён и файл существует — как сейчас для RULES_LOG).

## 7. P8-5: секция OBSERVE в спеке (точки наблюдения — до RED)

**Цель:** мутант выживает только там, где нет **ни одной** точки наблюдения. Заставим точки наблюдения существовать до кода и до red.cmd.

### Формат спеки

```
OBSERVE:
- return: load_average() → Some(значение при валидном /proc/loadavg) / None при мусоре
- state: HARNESS_MUTATE_MAX_LOAD читается один раз, границы 0.1/мусор/отрицательное
- log: «env-blocked: <why>» в логе гейта

RED: cargo nextest run load
RED-EXPECT: ...
```

4 типа точек: `return`, `side-effect`, `state`, `log`. Маркированный список после строки `OBSERVE:` — точки наблюдения перечисляются **до** формулировки `RED:`. Спека-задача уже отдаёт автору «что делать»; OBSERVE заставляет перечислить «чем это будет проверяться» до того, как автор напишет тест (или отдаст агенту `devh auto`).

### Реализация (точки)

- `commands/new.rs::observe_from_spec` — симметрично `red_from_spec`/`red_expect_from_spec`: буллеты (`- `) сразу после строки `OBSERVE:`. Записывается файл `observe.md` в item-dir (одна точка на строку). Префикс не пересекается с `RED:`/`RED-EXPECT:` — разбор независим, юнитом.
- `commands/new.rs::create_item` (и терминальный путь `devh new`) — писать `observe.md` рядом с `red.cmd`/`red-expect`.
- `prompt.rs::agent_prompt` — если `observe.md` есть, после блока RED-пруфа:
  `Точки наблюдения фичи (OBSERVE спеки, сформулированы до RED): … — каждый пункт обязан иметь ассерт в твоих тестах; тест, не проверяющий ни одной точки, тестом фичи не считается.`
- `devh doctor` — мягкая проверка (не гейт): `cfg.mutate.is_some()`, а у спеки нет OBSERVE → «спека без точек наблюдения: тесты рискуют быть слепыми; перечисли return/side-effect/state/log до RED».
- Шаблон спеки (док/вывод `devh new`) — OBSERVE-секция с примером одной строки.

OBSERVE **не** гейт и **не** условие: RED остаётся вратами (P7-1.1), мутационный вердикт остаётся истиной (§8); OBSERVE — про то, что автор до кода назвал точки наблюдения.

### Приёмка P8-5

- юнит: `observe_from_spec` на спеках c/без OBSERVE/c RED-смешением;
- интеграция: `create_item` со спекой с OBSERVE → `observe.md` создан; `agent_prompt` содержит точки; спека без OBSERVE → промпт без блока (не падает).

## 8. Честность и границы петли (слой ограничений, не фича)

1. **Промпт — ускоритель, гейт — истина.** Правила и hot-spot снижают число fix-раундов (агент реже оставляет слепые зоны с первого раза) — и только. Мутационный вердикт, DOOM/SAMPLE, MIN_KILL не меняются ни на строку. Новые классы слепоты гейт продолжит находить — петля и должна питаться свежими выжившими; остановка потока выживших = сигнал, что дистилляция слепа или гейт ослаб.
2. **Бюджет промпта.** Активный слой RULES ≤ 12 классов; hot-spot ≤ 3 файл одной строки. Инстансы в промпт не идут никогда (очередь/тикеты — туда и то руками через `tickets --import`, с обязательной red-идеей).
3. **Правило ≠ инцидент.** В RULES разрешены только формулировки классов без `file:line`. Перенос координат — регресс слоя (проверка при дистилляции — человеком, по правилу приёма §4).
4. **Авто-идея red-теста — триггер, не тест.** Строка очереди обязана пройти человеческое уточнение в тикете («ассерт точного значения» — направление, не готовая строчка ассерта).
5. **Killmap не карает.** kill-rate файла не влияет на гейт, MIN_KILL и merge — он лишь говорит агенту «пиши тут плотнее». Иначе hot-spot превращается в скрытый second гейт с другой пороговой семантикой.
6. **RED-выжившие ≠ кодовые.** red-mutation меряет качество спеки, не кода; помечены `[red-mutation]` и дистиллируются отдельными классами (напр. `blind:red-asserts` — «RED-тест ассертит именно то, что падает» — соседство с P7-1.1, не путать).
7. **Параллельные сессии.** `observations.md`, `killmap.json`, `survivors-seen.json` — под тем же `GlobalLock`, что и очередь; append единственный (никаких batch-read-modify-write вне лока).

## 9. Порядок, цена, приёмка

| # | Что | Цена | Первый шаг | Приёмка |
|---|---|---|---|---|
| P8-1 | survivors → observations.md + seen + killmap + config + tickets-текст | ~2–3 ч | парсер `outcomes.json` в `core/survivors.rs` (фикстура) | юнит на парсер/дедуп + интеграция A/B («ослабили max_load → очередь») |
| P8-5 | OBSERVE-парсер + `observe.md` + инжект в промпт + doctor + шаблон | ~1–1.5 ч | `observe_from_spec` + юнит (симметрия RED) | парсер/инжект; спека без OBSERVE не ломается |
| P8-3 | hot-spot пул в `agent_prompt` + таблица в `hint` (killmap уже есть с P8-1) | ~1–2 ч | пул из killmap (bounded) | 5 файлов → 3 в промпте; пусто → нет блока |
| P8-4 | `devh survivors` (группы + `--rules` + пенсия) + строка survivors в RULES_LOG | ~1–2 ч + регулярная часик-практика | группировка `survivors.log` | пенсионеры печатаются; merge пишет строку сессии |
| — | Итого кода | **~6–9 ч** | — | — |

**Порядок:** P8-1 → P8-5 → P8-3 → P8-4. P8-1 — данные потекли немедленно (очередь самонаполнится уже с первого гейта). P8-5 второй, потому что меняет производство новых спек (самый ранний компаундинг). P8-3 требует накопленной killmap. P8-4 — тулинг поверх истории.

Почему так, а не «сразу все»: каждый шаг независим и откатываем одной строкой конфига/промпта; ни один не меняет вердикт — сьют не краснеет от незавершённой петли.

**Ирония приёмки (к каждому шагу):** любой новый модуль в `devharness/src` сразу попадает под собственный мутационный гейт (batch `{files}` / `--in-diff`). Значит `survivors.rs` обязан убивать своих мутантов — иначе гейт его не примет, и это ровно тот класс «обёртки получают контракт-тест» (§4) в действии. Тесты на парсер — с точными ассертами (жанр, строка, дедуп), не `is_ok()`.

Вернуть тест → повторный прогон (после фикса seen сбросить через `--reset`) → выживший пропал. Оба наблюдения — в журнал `docs/rust_build.md` (как §9.x в P7).
